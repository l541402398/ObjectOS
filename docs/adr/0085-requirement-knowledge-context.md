# ADR-0085 — Reviewed organization knowledge in requirement planning and execution

Date: 2026-11-07 (America/Los_Angeles). Status: authorized by the user's request to continue K2.
Base: `168c9ba963d5b17ab62a615f10bcdab44a2c8fba`.

## Decisions

1. Extend the existing organization Settings surface with inline knowledge list/detail/editor/history and explicit publication confirmation. Add an organization-reference section in the existing requirement workspace. Preserve approved Premium Liquid Glass tokens, shared components, Motion/reduced-motion behavior, inline settings navigation and the protected Design Lab. This is an additive functional feature, not a visual migration or backend change for styling.
2. Append SQLite migration 45 only. Persist a requirement-scoped reference binding: authenticated server/account/organization, selected shared project, up to eight document/version/checksum references and human reasons. Store no organization bearer or raw knowledge body in this table. Default remains local; logging in never uploads or associates existing personal projects. Selecting a shared project authorizes knowledge use for this requirement only, not Worker/file/Shell/Git access.
3. Add a strict server resolve endpoint for exact selected versions. Recheck current organization and active-project membership, document visibility, published status and checksum under the existing lock. Reject revoked/deprecated/unknown versions or mismatches without substituting a newer/older version. Bound source titles plus bodies to 24,000 characters; citation fields and human reasons have separate per-field bounds. Ask for fewer sources rather than silently dropping evidence.
4. Keep organization credentials in Main. Add a single typed Runtime→Main `knowledge_request` / `knowledge_response` exchange over the existing child-process pipes, not a generic HTTP/FS/secret bridge. Main verifies current server/account/organization and validates bounded output. No renderer method can invoke this host channel. Requests time out and are rejected on shutdown/child replacement; no automatic retry or personal-mode fallback. Existing protocol-1 frames remain compatible; an absent host resolver fails closed for opted-in requirements.
5. Resolve references online for planning, revision planning and Native Agent execution. At the first planning/run use, freeze the selected reference revision, including a null binding for personal requirements. Reject subsequent changes; a new requirement is needed for a new reference set in this slice. Persist only citation metadata in plan/Run audit, never raw source bodies. Bodies are transient model reference data, explicitly subordinate to execution policy. Existing local requirement documents and model-produced analysis remain existing local artifacts.
6. Recheck authority before every model request/correction and every tool execution, including after human approval. Logout/switch/offline/revocation blocks new access; no cached fallback. Native requirement-analysis/technical-design and subsequent workflow nodes reuse the same Runner, policy, approval and persisted artifacts. External CLI execution cannot safely enforce this reference boundary in K2 and is rejected for opted-in requirements.
7. Planning uses the selected evidence as additional bounded context without embedding source bodies into persisted plan goals. Plan approval rechecks references and retains the existing atomic task/dependency transaction. A knowledge citation does not approve the generated plan, technical design, file write, test process or Git action.

## Acceptance

Real PostgreSQL exact-version resolution and negative authorization tests; SQLite migration preservation, optimistic reference editing, frozen versions and no-body/no-secret persistence; Main stale-context and host-channel rejection; actual model-prompt capture proving evidence use; revocation before a second model request and approval-resumed writes; personal-mode regression; real Electron Settings/requirement interactions with scoped test accounts and keyboard/dirty-close checks; 1440/1024 light/dark/125% screenshots, comparison and a11y. Run every root-required command, package smoke, commit evidence with implementation and push. Do not mark K3 knowledge writeback, K4 person assignments, real external model acceptance or K5 two-computer production deployment as completed.
