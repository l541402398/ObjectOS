## 1. 一句话结论

**ProjectOS 已经是可运行、功能较丰富的 V1.7 桌面产品雏形，但不能按 V1.6 正式实施说明书的 P0 验收基线宣称“实现完整”。**

- V1.1–V1.5 的核心链路大部分可用：项目/任务、原生 Agent Loop、审批、运行审计、跨会话、AI 连接、扫描/计划/图、Worktree、质量门禁、FTS、自主运营。
- V1.6 的中心 P0 没有闭环：自定义 Agent 没有真正绑定到 DAG/自主运营，AgentRun 没有配置快照，调度前没有完整预检。
- 更严重的是：CLI/ACP/外部 Agent 执行路径绕过了 ProjectOS 的 **Approval、ToolCall 审计和 task lease**，违反 AGENTS.md 和 ADR-0005 的核心不变量。

因此：**修复优先级不是视觉打磨，而是执行安全、审计和调度一致性。**

## 3. P0 缺口与修复要求

### P0-1. 外部 Runtime / ACP / 外部 Agent 绕过 Approval、ToolCall 和 Lease

**现状证据（行号基于 717b10c）：**

- ACP permission handler 只按 Agent 的 `files/shell/network` 权限直接返回 optionId，没有创建 ProjectOS Approval，也没有 ToolCall：
  `apps/runtime/src/agent-runner.ts:377-388`
- `AgentDefinition.run` / Runtime 测试入口直接 spawn CLI，只写 Run/Message/RunStep，没有 Approval/ToolCall：
  `apps/runtime/src/runtime-run.ts:84-118`
  `apps/runtime/src/runtime-executor.ts:28-84`
- 外部 Agent runner 接受 `taskId` 创建 Run，但不获取 task lease、不创建 TaskAttempt、不创建 Approval/ToolCall：
  `apps/runtime/src/external-runner.ts:90-150`
- 对照：原生循环在 `apps/runtime/src/agent-runner.ts:901-942` 创建 ToolCall/Approval；这是目前唯一完整的审计路径。

**违反的约束：**

- AGENTS.md：“Every side effect is recorded as a ToolCall before and after execution.”
- AGENTS.md：“File writes, process execution, Git writes, and deploys require policy evaluation and human approval.”
- ADR-0005：“Run 在工具执行前写 ToolCall 意图与 argsHash/idempotencyKey，执行后写结果。”
- ADR-0005：“失去 Lease 的执行者不得提交状态。”

**必须改成：**

1. 设计一个覆盖 native / CLI / ACP / external 的统一副作用网关（建议命名 `RuntimeToolGateway` 或 `ExecutionGateway`）：
   - 执行前写 ToolCall（含 `argsHash`、`idempotencyKey`、policy/Approval 关联）。
   - 需要审批的操作必须先进入 Approval，Run 进入 `waiting_approval`；批准后才执行。
   - 执行后写结果/错误/退出码。
2. ACP 的 `session/request_permission` 不能直接返回 optionId：
   - 映射成 ProjectOS Approval；
   - 用户批准后再返回对应 option；
   - 拒绝时返回拒绝/空选项；
   - 记录 ToolCall 和事件。
3. 外部 CLI / 外部 Agent：
   - 至少对整个执行建立 ToolCall（prompt hash、workspace、worktree、exit code、diff artifact）。
   - 写模式必须经过显式 Approval；只读模式也要记录 ToolCall。
   - 如果 CLI 内部工具对 ProjectOS 不可见，必须在 ADR 中写明“不可逐工具审计”的限制，并提供等价的 run 级审批 + worktree 隔离 + diff 审计；不能静默假装已审计。
4. `external-runner` 必须：
   - 创建 TaskAttempt；
   - 获取/续约 task lease；
   - 结束/失败/取消时释放 lease；
   - 续约失败时停止并进入 `needs_reconciliation` 或 `failed`。

**验收测试（必须新增）：**

- ACP permission request → Run `waiting_approval`，Approval 表有记录；批准后工具执行；拒绝后不执行。
- CLI Runtime 写模式无 Approval 时被拒绝；批准后执行并产生 ToolCall 记录。
- 外部 Agent 运行 task 时存在 TaskAttempt 和有效 lease；第二个并发执行被拒绝。
- Run 详情能查到每个批准操作的 ToolCall，而不是只有 RunStep。

### P0-2. 自定义 Agent 没有真正接入 DAG 和 V1.4 自主运营

**现状证据：**

- `PlannedTaskSchema` 没有 `agentId`：
  `packages/contracts/src/orchestration.ts:35-44`
- 计划批准仍按角色硬编码映射到内置 Agent：
  `packages/planning/src/index.ts:3-13`
  `apps/runtime/src/orchestration.ts:259`
- 编排 Inspector 只显示 Agent ID，没有“执行 Agent”选择器：
  `apps/desktop/src/renderer/src/features/orchestration/pages/OrchestrationWorkspace.tsx:766-779`
- V1.4 `startRepair` 生成计划的角色也走同一映射，无法指定修复 Agent：
  `apps/runtime/src/dispatcher.ts:192-201`

**当前是“部分可用”而不是“完全不可用”：**

任务看板可以在计划批准后改 `assigneeAgentId`，编排会使用新 assignee。但这不是 V1.6 要求的节点级 AgentAssignment + 角色默认绑定 + 统一 Resolver。

**必须改成：**

1. 在计划任务上保存 `agentId`（或新增 `AgentAssignment`，支持 node 级、role 级默认）。
2. 计划更新/批准时校验：
   - Agent 存在且 `status === 'active'`；
   - 绑定的 Runtime 可用；
   - Skills/能力兼容（至少记录警告或阻断原因）。
3. 批准创建 Task 时：节点显式 `agentId` 优先；否则回退角色默认；保留旧计划无绑定的兼容路径。
4. DAG Inspector 增加 Agent 选择器，展示真实可用性/原因；选择后保存 agentId，不保存展示名。
5. V1.4 自动化设置增加可选 `agentId`；`startRepair` 使用该 Agent；没有配置时走旧默认。
6. 去掉调度器里“角色 switch/case 决定执行者”的新路径；`agentForPlanRole` 只保留为旧数据兼容默认。

**验收测试：**

- 自定义 Agent 绑定到计划开发节点 → 批准 → Task.assigneeAgentId 是该自定义 Agent → 编排实际运行该 Agent。
- 同一计划不同节点绑定不同 Agent。
- 旧计划没有 agentId 时仍按原默认角色运行（兼容）。
- V1.4 修复计划可指定 Agent，未指定时回退默认。
- E2E 覆盖至少 E2E-02/03/05/07 的核心路径。

### P0-3. AgentRun 没有执行快照，运行中编辑会影响进行中的 Run

**现状证据：**

- `RunSchema` 只有 `agentId`，没有 `agentConfigVersion`、persona/skills/runtime/permission/workflowNodeId 等快照：
  `packages/contracts/src/entities.ts:150-166`
- `agent_config_versions` 只在保存 Agent 时插入，没有读取路径：
  `packages/persistence/src/store.ts:1569`
- 原生循环每次 `buildMessages` 重新读取当前 AgentDefinition/Skills：
  `apps/runtime/src/agent-runner.ts:423-473`
- `startRun` 只保存 promptMessageId/workspaceRoot 等上下文，不冻结 Agent 配置：
  `apps/runtime/src/agent-runner.ts:200-215`

**后果：**

- 运行中编辑 Agent 的人设、Skills、权限，下一轮模型调用会使用新配置；
- 无法复现历史 Run 的真实配置；
- V1.6 E2E-04 “旧任务保持旧快照”不成立。

**必须改成：**

1. Run 创建时冻结快照（新增 `run_snapshots` 表或扩展 `agent_runs`，建议独立表）：
   - agentId、agentConfigVersion；
   - personaHash / 有效 prompt 引用；
   - skillsVersionSet；
   - runtimeProfileId / adapterVersion；
   - model/provider；
   - permissionPolicySnapshot；
   - worktreeId；
   - workflowNodeId（如果计划节点）。
2. 原生循环和 Runtime 执行都从快照构建 prompt/permissions，不再实时读取可变 AgentDefinition。
3. `agent_config_versions` 必须有读取接口；Run 详情能展示使用的版本。
4. 重试时显式选择“沿用旧快照”或“创建新 attempt 用新快照”，并记录 lineage。

**验收测试：**

- 启动 Run → 修改 Agent 人设/Skills/权限 → 继续同一 Run 的下一轮：仍使用旧快照。
- 新 Run 使用新配置。
- 历史 Run 详情展示 agentConfigVersion，并与其快照一致。
- 如果 Agent 被删除/归档，历史 Run 仍可查看快照。

### P0-4. Lease/fencing、依赖门禁在手动 `run.start` 路径失效

**现状证据：**

- `startRun` 先创建 Run、TaskAttempt，并把任务移到 `running`，之后才获取 lease：
  `apps/runtime/src/agent-runner.ts:181-261`
- lease 获取失败时只把 Run 置 `failed`，没有回滚任务/TaskAttempt：
  `apps/runtime/src/agent-runner.ts:253-261`
- lease 续约失败只记录 warning，不终止 Run：
  `apps/runtime/src/agent-runner.ts:297-306`
- `moveTask` 只校验 `expectedVersion`，不接收/校验 fencing token：
  `packages/persistence/src/store.ts:638-654`
- `startRun` 直接调用 `store.moveTask`，绕过 `TaskService.move` 的依赖门禁：
  `apps/runtime/src/agent-runner.ts:225-237`
  `packages/application/src/task-service.ts:133-140`

**后果：**

- 取 lease 失败后任务卡在 `running`、TaskAttempt 残留 `running`；
- lease 丢失后旧执行者仍可提交任务状态；
- 有未完成依赖的任务可以通过手动/API `run.start` 启动；
- 两个 Session 同时运行同一 Task 时，第二个会在创建 run/attempt 后才失败。

**必须改成：**

1. 先获取 lease，再创建 Run/TaskAttempt/移动任务；或者把 lease 获取放进同一个事务，失败则整体不落库。
2. lease 续约失败：立即 abort Run，标记 `failed` 或 `needs_reconciliation`，更新 TaskAttempt，不允许后续提交。
3. 业务写路径带 fencing 校验：至少 `moveTask`/任务完成/验收提交要校验当前 lease holder+token；或者所有写入经过一个 lease-aware 的 TaskService。
4. `startRun` 使用 `TaskService.move`（或在移动前显式检查 `blockedBy`），保留“依赖未完成不能 running”的门禁。
5. 增加“同一 Task 两个 Session 并发启动”的集成测试，断言第二个不留下孤儿 Run/Attempt。

**验收测试：**

- 两个 Session 同时对同一 Task `run.start`：第二个返回冲突；任务状态/Attempt 不被污染。
- lease 获取失败：无 Run/Attempt/任务状态残留。
- 模拟 lease 续约失败：Run 停止，旧执行者不能提交任务状态。
- 有未完成依赖的任务：手动 `run.start` 返回冲突。

### P0-5. Runtime 不可用时静默回退，预检不完整

**现状证据：**

- `runtimeReady` 为 false 时直接走模型 Provider：
  `apps/runtime/src/agent-runner.ts:164-176`
- 没有检查 Agent 是否 archived、Skills 是否兼容、Runtime 能力是否满足任务：
  `apps/runtime/src/agent-runner.ts:143-176`
- `AgentDefinition.status` 实际只会是 `active`；没有归档流程：
  `apps/runtime/src/agent-studio.ts:82-112`

**后果：**

- 用户以为在运行 Codex/Claude Code，实际静默走了内置模型；
- Runtime 未安装、认证失败、能力不兼容都不会在调度前阻断；
- 违反 V1.6 §20.8 “调度前阻止或进入待处理状态，不自动静默切换”。

**必须改成：**

1. 如果 Agent 显式绑定了非 native Runtime：
   - Runtime 不存在/不可用/认证失败/能力不兼容 → 阻断并返回可操作错误；
   - 不自动回退 Provider，除非有显式策略或用户确认。
2. 预检：Agent 存在且 active、Runtime available、Skills 兼容、凭据有效、Worktree/目录可用、预算/并发允许。
3. `AgentDefinition.status` 支持 `archived`；归档 Agent 不能新建 Run，但历史 Run 保留。
4. 旧 Agent/旧计划没有显式 Runtime 绑定时，保留原有 Provider 兼容路径（这是允许的回退）。

**验收测试：**

- 绑定未安装 Runtime → `run.start` 阻断，Run 不创建。
- 绑定认证失败 Runtime → 阻断并显示原因。
- archived Agent → 阻断。
- 没有 Runtime 绑定的旧 Agent → 仍走原默认 Provider（兼容）。
