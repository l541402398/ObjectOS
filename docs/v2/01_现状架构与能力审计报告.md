## 0. 结论摘要

1. **ProjectOS 当前是一个真实可运行、测试较扎实的“AI 研发执行工作台”，还不是“项目全生命周期管理与自主运营平台”。** 它已经打通项目、需求、任务、计划、Agent、运行、审批、交付物、知识库和研发健康检查的主链路；但版本、发布、环境、部署、线上监控、故障事件、运维作业这些 V2.0 必需领域，在当前代码中基本不存在。
2. **生命周期确实是单轨的。** `projects.current_stage` 是唯一生命周期字段，8 个阶段按固定顺序推进，`advanceStage` 不允许回退，并校验此前所有阶段门禁（`packages/contracts/src/entities.ts:28-40`、`packages/application/src/project-service.ts:184-214`、`packages/domain/src/task.ts:254-320`）。一个项目无法同时表达“维护线上 v1.4、开发 v1.5、处理 P1 故障、规划 v1.6”。
3. **没有产品版本、环境、发布、部署、故障、服务、告警、Runbook 的真实模型。** 在 `packages/contracts/src` 全量检索 `environment|deployment|incident|telemetry|runbook|release`，只命中 8 阶段枚举、`release-note` 交付物类型和阶段门禁文案，没有对应实体、表、API 或页面（见 §4、§7）。
4. **现有 “Revision” 是计划修订号，不是产品版本。** `PlanDraft.revision` 与 `plan_revisions` 表达的是同一计划的新草稿版本（`packages/contracts/src/orchestration.ts:173-193`、`packages/persistence/src/migrations.ts:436-449`），不能替代 V2.0 的 ProductVersion / Release。
5. **Agent 执行平台是当前最成熟、最应保留的资产，但执行入口尚未完全收口。** Planner、Replanner、AgentAssignmentResolver、OrchestrationScheduler、AgentRunner、PlanGrant、Policy/Approval、Run 快照、Lease/Fencing 都是真实实现，且只有一套：`new PlannerService`、`new ReplanService`、`new OrchestrationScheduler` 各出现一次（`apps/runtime/src/dispatcher.ts:95-135`）。没有发现第二套 Planner、Scheduler、Agent Registry 或 Runtime Registry。**但 `runtime.execute`/`runtime.acpPrompt` 可绕过 Run/ToolCall/审批/预算/租约，CLI/ACP Runtime 又未使用计划 Worktree；这是 V2.0 前必须封堵的 P0 执行边界缺口（见 §6.5）。**
6. **“自主运营”目前是研发健康检查 + 修复提案，不是生产运维。** 检查内容是 Git 工作区、lint/typecheck/test/build、阻塞任务和可选依赖审计（`apps/runtime/src/operations.ts:226-326`）；没有线上指标、日志、链路、告警、故障事件、值班或 Runbook。
7. **真实 API 面很大，但领域缺口同样明显。** `ApiSchemas` 共 171 个方法（`packages/contracts/src/api.ts:298-1092`），其中 project/plan/runtime/task/operations 占大多数；没有任何 version/release/environment/deployment/incident/observability 方法。
8. **UI 只有 15 个页面、13 个设置分区，信息架构仍是“单项目 + 单阶段 + 研发现场”。** 导航分组为工作台/工程/全局（`apps/desktop/src/renderer/src/components/AppLayout.tsx:285-317`），缺少版本、路线图、发布、环境、部署、故障、服务目录、可观测性入口（`apps/desktop/src/renderer/src/router.tsx:44-75`）。
9. **已批准的 0686c41 视觉基线没有进入当前分支。** `git merge-base --is-ancestor 0686c41 HEAD` 返回失败；实际方向是 **HEAD 比基线早 6 个提交**（`git rev-list --count HEAD..0686c41` = 6，`0686c41..HEAD` = 0），基线新增的 `features/design-lab/*`、`next-ui/*` 等资产在 HEAD 中不存在，`git diff --stat 0686c41 HEAD` 因此显示 3284 行差异。当前 UI 是 Design Lab 之前的 V1.7 演进线，不能宣称“保持了已批准基线”。
10. **本轮实际测试通过：49 个测试文件（48 passed、1 skipped）、265 passed、3 skipped、74.95s。** 但测试主要覆盖研发执行、审批、租约、预算、计划/重规划、团队接力；没有版本/发布/部署/故障/观测的测试，因为对应领域尚不存在。
11. **分支与工作区卫生是近期风险。** 10 个 worktree、15 个本地分支、4 个 tag；主工作区有 5 项未跟踪文件，`feature_dev_ux`、`perf/...`、`next-ui-full-migration` 各有未提交/未跟踪改动。任何“整理仓库”的动作都可能破坏其他会话成果，V2.0 启动前必须冻结并建立基线分支策略。
12. **总体判断：** 不应重写执行内核，也不应把现有系统直接扩成“无限范围的大重构”。正确路径是**在现有单写者、单调度器、单 Planner、统一审批与审计之上，增量增加“产品/版本/环境/发布/部署/故障”领域层，并把生命周期从单字段改为“项目姿态 + 多版本/多活动并行轨道”**。这将是 V2.0 一期的核心。

### 3.2 进程与信任边界

```text
React Renderer（无 Node/FS/DB/Shell）
  │ 命名 preload API + Zod
Electron Main（窗口 / IPC / secrets / Runtime supervisor）
  │ NDJSON over stdio
Node Runtime（application / agent loop / tools / SQLite 唯一写者）
  ├── SQLite（WAL、FK、迁移校验）
  ├── 本地工作区（FS / Git）
  ├── Provider（HTTP 出站）
  └── 受审批工具进程
```

**已真实实现的架构不变量：**

- Renderer 只能通过命名 preload API 访问后端，不能 `invoke(channel, any)`（`apps/desktop/src/preload/index.ts`、`packages/contracts/src/desktop-api.ts`）。
- Main 与 Runtime 双重 Zod 校验（`apps/runtime/src/dispatcher.ts:522` 起、`packages/contracts/src/api.ts`）。
- Runtime 是 SQLite 唯一写者；Main 不直接写业务库（ADR-0001）。
- 任务租约使用单调 fencing token；Run 先取全局 Agent 槽位与任务租约，再创建 Run/Attempt（`apps/runtime/src/agent-runner.ts:341-361`）。
- Run 创建时冻结 `run_snapshots`（`apps/runtime/src/agent-runner.ts:332-340,390-391`）。
- 写文件/执行命令先创建 Approval 与 ToolCall；拒绝/过期不执行（`apps/runtime/src/agent-runner.ts:2192-2248`）。
- 未知外部副作用进入 `needs_reconciliation`，不自动重试（`apps/runtime/src/agent-runner.ts:2691-2692,2895-2928`）。

## 5. 生命周期、门禁与并行场景

### 5.1 八阶段与门禁

| 阶段 | 门禁要求 | 代码 |
|---|---|---|
| ideation 构思 | 项目存在即可 | `domain/src/task.ts:261-266` |
| requirements 需求 | ≥1 条 approved requirement | `271-274` |
| architecture 架构 | ≥1 条 accepted ADR | `275-278` |
| planning 规划 | ≥1 个 milestone | `279-282` |
| implementation 实现 | ≥1 个 ready task | `283-286` |
| testing 测试 | ≥1 个 review/done task | `287-290` |
| release 发布 | ≥1 个 verified Artifact | `291-294` |
| maintenance 维护 | ≥1 个 release 类 Artifact | `295-298` |

这些门禁本身是合理的“研发阶段检查”，但它们是**项目级、串行、单向**的。V2.0 需要把它们改造成**可绑定到 Version / Iteration / Release / Deployment / Incident 的证据门禁**，而不是项目全局状态机。

### 5.2 并行场景压力测试

假设一个真实项目：

- 线上 v1.4 处于维护期，需要修一个安全补丁；
- v1.5 正在开发新功能；
- 生产出现 P1 故障，需要立即定位与热修；
- 同时在规划 v1.6 的范围。

当前模型能否表达？

| 活动 | 需要的状态 | 当前模型 | 结果 |
|---|---|---|---|
| 维护 v1.4 | version=1.4, phase=maintenance, hotfix release | 无 version；只有 `currentStage` | **不能** |
| 开发 v1.5 | version=1.5, phase=build, iteration=2026-Q4-2 | 无 version/iteration | **不能** |
| 处理 P1 | incident=INC-xxx, sev=1, status=mitigating | 无 incident | **不能** |
| 规划 v1.6 | roadmap item / discovery | 无 roadmap | **不能** |
| 同一项目多活动并行 | 多 track 并存 | 单 `currentStage`；门禁要求全项目前序完成 | **不能** |
| 活动之间关联 | incident → hotfix deployment → patch release → postmortem | 无关联实体 | **不能** |

**结论：** 当前项目生命周期是“一次性开发流水线”的模型，而不是“持续产品运营”的模型。V2.0 必须引入**项目姿态（posture）+ 版本生命周期 + 多活动轨道**，`currentStage` 只能保留为 **legacy 兼容事实**，不能再做全局门禁权威；用户当前关注对象放独立 `project_focus`，不得把 `currentStage` 改名或当作 UI 焦点。

### 6.3 Scheduler 真实能力

- 启动前校验计划已批准、Grant 有效、预算、任务存在（`orchestrator.ts:178-220`）。
- 每 tick：
  - Grant 失效即暂停，不启动新任务（`951-979`）；
  - 计划级墙钟预算（`980-984`）；
  - `needs_reconciliation` 即暂停等人工（`998-1010`）；
  - 失败任务按退避重试，耗尽后失败并触发 Replan（`1011-1042`）；
  - review 任务执行质量门禁、证据评估、自动完成/补证/暂停（`1044-1223`）；
  - 全部 done 才完成计划，并生成 diff Artifact（`1229-1250`）；
  - 依赖未完成不提升；单 Agent 单 Run；并发槽位（`1253-1317`）。
- 真实边界：
  - 只针对“已批准计划创建的任务”，不是通用工作流引擎；
  - 质量门禁是项目脚本（lint/typecheck/test/build），不是发布/部署/线上健康；
  - 自动验收基于 Artifact/文件/运行证据（`completion-evidence.ts`），不是业务验收人。

### 6.4 执行安全与残留风险

**已做对的：**

- 原生循环：写文件/命令/ Git 写需 Approval；ToolCall 先写意图再执行；Run 进入 `waiting_approval`。
- ACP `session/request_permission` 创建 ProjectOS Approval，而不是直接返回 option（`agent-runner.ts` + `tests/agent-runner-guards.test.ts`）。
- 外部 Agent 获取 task lease、创建 Attempt、记录 run 级 ToolCall、Worktree 隔离（ADR-0009）。
- 审批过期会置 `expired`、失败 Run、释放租约（`agent-runner.ts:2207-2247`）。
- 预算/步骤/工具调用硬限制；超限终止并写审计步骤（R1 测试）。

**残留风险：**

1. **外部 CLI 内部工具无法逐工具观测**：只能做 run 级 ToolCall + Worktree + diff 审计；这是已承认的限制（ADR-0009），但不能宣称“每个副作用都可逐工具审计”。
2. **外部 Runtime 的审批覆盖仍依赖适配器实现**：如果未来新增 CLI/ACP 适配器不经过统一网关，仍可能绕过。V2.0 应把“统一副作用网关”作为硬约束。
3. **`agent-runner.ts` 单文件 2930 行**：审批、工具、循环、恢复、压缩耦合；新增部署/运维工具会继续放大风险。
4. **Planner 只服务研发计划**：没有 PlanKind/领域工作流概念；发布、故障、运维计划无法复用同一规划器。
5. **没有环境/发布上下文**：Run 快照冻结了 Agent/Runtime/权限/模型，但不冻结“目标环境/版本/变更单”，未来部署类 Run 不可审计。

### 9.2 对 ProjectOS 架构影响最大的五个发现

1. **AWR 的证据模型需要拆维，而不是照搬。** AWR 在 `crates/awr-store/migrations/002_domain.sql:244-263` 定义 `evidence.level` 为 `designed / implemented / locally_verified / real_environment_validated / release_candidate / released / unknown`，并绑定 artifact SHA256、来源 revision、branch、verified_at。该枚举把“验证保证程度”和“产品生命周期”压在一个维度上；ProjectOS 应拆成 `EvidenceType`、`VerificationStatus`、`Assurance`、`LifecycleStatus`（属于主体而非证据）和 `Provenance`。AWR 的可取之处是“证据必须有来源/哈希/等级”，不是这个线性枚举本身。
2. **AWR 的“硬交付依赖 + 采用凭证”能解决版本/工作流之间的证据链。** `012_delivery_deps.sql:4-26` 的 `hard_delivery_dependencies` 绑定 provider/consumer workstream、completion receipt、contract SHA256、artifact SHA256；`export_authorizations`/`adoption_credentials` 区分授权、采用、失效。ProjectOS 的 Release/Deployment/Incident 应采用“精确制品 + 回执 + 采用凭证”的模式，而不是只存一个版本号。
3. **Orchestrator.inc 的“durable facts, derived status”验证了 V2.0 的项目姿态设计。** 它明确“display status is never stored；durable facts + derived status”，并用 `lifecycle.Manager` 作为唯一事实写入口、CDC 广播、observer 轮询 SCM/runtime（`docs/architecture.md:40-65,728-890`）。ProjectOS 的 `ProjectPosture` 也应从版本/发布/部署/事故事实派生，不能新增一个可随意改写的“项目阶段”字段。
4. **Aperant 的“复杂度分层 + QA 循环”适合 QA/交付工作流，但不能照搬其自动合并。** `spec-orchestrator.ts` 按 simple/standard/complex 选择阶段；`build-orchestrator.ts` 走 planning→coding→qa_review→qa_fixing；`qa-loop.ts` 有多轮 QA、复发问题与连续错误升级、人工反馈。ProjectOS 应借鉴“复杂度和 QA 升级策略”，但保留人工发布门禁，不采用 50 轮自动循环/自动合并默认值。
5. **Plane 的 Cycle/Module/StateGroup/IssueView 验证了“迭代 + 范围容器 + 保存视图”的 IA。** `cycle.py`、`module.py`、`state.py`、`view.py` 显示：Cycle 有时间盒和 progress snapshot；Module 有独立状态；Issue 通过 StateGroup（backlog/unstarted/started/completed/cancelled/triage）聚合；IssueView 存 query/filters/display properties。ProjectOS 的 Roadmap/Iteration/Work 页面应采用这些概念，但不复制 AGPL 代码。

### 9.3 许可证与复用结论

- **AGPL-3.0（Plane、Aperant、Grafana）**：只借鉴架构/IA/流程思想，**不复制代码、组件、样式或提示词资产**。ProjectOS 是 MIT，AGPL 代码进入会带来强 copyleft 风险。
- **Apache-2.0（Orchestrator、AWR、Argo CD、Rundeck）**：可在保留 NOTICE/许可证的前提下复用少量代码，但优先“独立实现/适配器”；本轮不引入任何外部运行时或服务端。
- **MIT（SigNoz，`ee/` 与 `cmd/enterprise/` 除外）**：可复用社区部分，但需保留版权；不引入 ClickHouse/采集器。
- **结论**：V2.0 不新增任何外部服务依赖；只吸收已验证的模型/状态机/边界设计，所有代码仍由 ProjectOS 自行实现。

> 本轮没有把“读过 README”当成“读过源码”；上述结论均引用了仓库内的模型/状态机/文档路径。许可证以仓库 LICENSE 实读为准。

## 13. 审计结论与对 V2.0 的直接约束

1. **保留执行内核，扩展领域层。** 不重写 Planner/Scheduler/AgentRunner/Policy；在它们之上增加 Product/Version/Release/Environment/Deployment/Incident/Service/Observability 领域。
2. **生命周期改为“姿态 + 轨道”。** `currentStage` 保留原名、仅作 legacy 兼容；项目健康/阶段由多版本、多迭代、多事故、多发布共同派生。
3. **一期只做基础，不做全套运维。** 一期应完成产品/版本/迭代/环境模型、项目姿态、版本上下文、路线图/导入，以及门禁 v2；发布/部署/故障/观测放在后续阶段，禁止用占位 UI 冒充已实现。
4. **先冻结视觉基线，再谈页面。** 0686c41 是视觉基线，但不在当前分支；V2.0 第一阶段必须先完成基线对齐与截图验收，之后才能新增页面。
5. **先补 ADR 与迁移方案，再写代码。** 至少需要：生命周期姿态、版本聚合、环境/部署、统一审批、适配器边界、本地优先/远程执行、视觉基线治理。
6. **所有“未实现”必须继续标注未实现。** V2.0 文档、UI 文案、演示数据都不得把发布/部署/运维描述成已完成。

10. **远程执行/数据保留**：远程 Worker 是否进入一期（建议不进入）？Run/事件/日志/指标快照保留多久？
