# ProjectOS organization control plane — A1 foundation

The normal entry point now uses PostgreSQL. It refuses to start without `DATABASE_URL`, a signing
secret of at least 32 characters, and the exact versioned schema. The existing A0 in-memory
`buildServer()` remains in `src/app.ts` exclusively for isolated PoC/regression tests; the deployment
entry never falls back to it.

## Run and migrate

Use Node 24 and PostgreSQL. Set the environment variables shown in `.env.example` with your own
credentials; environment files are not automatically loaded. Do not commit deployment secrets.

```powershell
pnpm build:server
pnpm --filter @projectos/server migrate
pnpm --filter @projectos/server start
```

A deployed JavaScript artifact can run `node dist/index.js --migrate` and `node dist/index.js` with
its production dependencies installed. The build bundles workspace contracts so deployment does
not depend on executing TypeScript source packages. The application does not provision PostgreSQL,
register OS services, obtain TLS certificates or deploy a public endpoint automatically.

Migrations run explicitly, inside a transaction and under a PostgreSQL advisory lock. Version 1
includes the schema generated by installed Better Auth 1.7.14 plus application tables; its checksum
is checked on every startup. A changed or unknown migration causes startup to fail. Make database
backups before deployment upgrades; future changes must add migrations rather than edit version 1.

`BETTER_AUTH_URL` must be an origin without a path, query, embedded credential or fragment. HTTPS is
required outside loopback. `HOST` defaults to `127.0.0.1`; use an explicitly configured HTTPS reverse
proxy for shared deployments. Fastify does not trust arbitrary forwarding headers.

## Delivered API

- Browser email/password sign-up and sign-in through Better Auth, plus server-rendered desktop
  registration/login and explicit consent. The browser pages use static Premium Liquid Glass
  materials, readable text, keyboard focus, system light/dark preference and no JavaScript.
- Desktop authorization uses a loopback callback, state, PKCE S256, single-use consent and codes.
  Only a one-time code appears in the callback URL. Bearer tokens are stored as SHA-256 hashes in
  PostgreSQL and can be revoked with `POST /v1/desktop/revoke`; sessions survive server restart.
- `GET /v1/me`, `POST /v1/organizations`, organization-scoped project creation/listing and member
  listing, invitation creation/listing/accept/reject, member role changes/removal, and project-member
  assignment. Lists are bounded (200 projects/members, 100 invitations).
- Organization membership never automatically grants project membership or local execution rights.
  Removing a member also removes their project memberships in the same transaction. Scoped writes
  lock the organization and recheck the actor's current role inside the transaction. An invitation
  can be accepted only once, by its addressed email, before expiry, while its inviter is still
  authorized, and with an independent 32-byte invitation code. Only a SHA-256 code hash is stored;
  the code is returned once to the inviter and never by the recipient's invitation-list endpoint.
  Wrong codes do not consume a valid invitation. Project ownership transfer is deliberately
  unavailable through the generic role API.
- Custom routes are rate-limited with bounded in-process IP buckets. Browser form posts reject an
  untrusted Origin/cross-site fetch. Vendor organization-management HTTP routes are disabled so all
  membership mutation goes through the audited API. Transport errors omit database/credential data.
  The browser authorization page permits form submission to itself and only the validated native
  callback's exact `127.0.0.1` origin/port, so Chromium can follow the consent POST redirect without
  a wildcard CSP allowance. Same-origin referrer policy preserves a valid Origin for same-origin
  form POSTs; an opaque `Origin: null` remains rejected.

Invitations appear in the recipient's signed-in workspace. The inviter shares the one-time code
through a trusted channel; this slice sends no email and does not claim email-ownership verification.
An email address or invitation ID alone cannot grant membership. It does not
implement organization asset publication, Worker dispatch, local-project import/linking, requirement
workspaces, workflow execution, refresh-token rotation, distributed rate limiting, database RLS,
or a production deployment/operations system. Those capabilities must not be inferred from A1 UI.

## Validation

```powershell
pnpm exec vitest run tests/org-persistent-server.test.ts
pnpm test:org
```

The persistence test starts an actual isolated loopback PostgreSQL cluster from the licensed
`embedded-postgres` development binaries; it does not use SQLite, an in-memory adapter, or a mocked
PostgreSQL implementation. It tests server restart, isolation, revocation, invitations, transaction
permission rechecks, schema checksums, rate limits and the browser registration/consent flow. Run the
PostgreSQL test as a non-root OS user. Temporary clusters are stopped and their own directories
removed afterward. The original 31 A0 tests continue to prove the separate historical PoC boundary.
